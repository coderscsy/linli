# OliviaSoul 可配置每日发信上限设计

日期：2026-08-31

## 背景与目标

当前本地服务在 `source/local-service/server.js` 中把每日发信上限硬编码为 3，发送和失败重发都会在余量为 0 时返回 HTTP 429。这个限制来自 OliviaSoul 的兼容实现，不是官方账号、Gemma 模型或模型网关的限制。

目标是让本地离线环境默认不限发信次数，同时保留可配置的有限上限。不得修改既有信件、记忆或回复任务数据，也不得依赖仍在线的官方服务。

## 方案比较

### 方案 A：服务端可配置，`0` 表示不限量（采用）

在现有 SQLite `settings` 表中增加每日上限设置。默认值为 `0`，表示不执行每日拦截；正整数表示实际有限上限。管理页提供数字输入框。官方游戏客户端要求 `remainingToday` 为正数才启用“写信”按钮，因此不限量模式返回兼容值 `9999`，服务端本身不进行次数限制。

优点：不需要再次修改压缩后的官方客户端；默认不限量；以后仍可恢复为 3 或其他数值；升级和测试边界清楚。缺点：官方客户端会显示“剩余 9999 封”，而不是文字“不限量”。

### 方案 B：固定改成 9999

直接把硬编码的 3 改成 9999。改动最小，但仍是硬编码，也不是严格不限量，用户无法在管理页调整。

### 方案 C：同时修改官方客户端显示“不限量”

服务端使用特殊哨兵值，并修改 `feapp.dat` 内的客户端逻辑和文案。显示最准确，但会增加对压缩前端资源的脆弱补丁，官方原始文件恢复与后续维护风险更高。

## 选定设计

### 服务端设置

- 新设置键：`daily_letter_limit`。
- 默认值：`0`（不限量）。
- 合法范围：`0` 到 `10000` 的整数。
- `0` 时，发送和重发都不因当日数量返回 429；API 中的 `remainingToday` 返回 `9999`，确保官方客户端按钮保持可用。
- 正整数时，沿用现有“本地自然日 + live 信件 + 排除失败状态 + 支持今日重置”的统计口径，返回真实剩余数。
- 429 文案使用当前配置值，例如“今天最多发送 5 封信”，不再硬编码 3。

### 管理 API 与界面

- `GET /admin/api/debug` 增加 `dailyLetterLimit` 和 `unlimitedRemainingValue`。
- 新增 `POST /admin/api/debug/quota/limit`，请求体为 `{ "limit": number }`；校验失败返回 HTTP 400，并且不修改原设置。
- 调试页“今日信件次数”卡片增加数字输入框和说明“0 表示不限量”。修改成功后立即刷新当前余量。
- 现有“重置今天信件次数”按钮保留；在不限量模式下可继续调用，但不会改变不限量行为。

### 数据与兼容性

- 复用现有 `settings` 表，不新增数据库表或迁移脚本。
- 已有 `quota_reset:*` 设置和历史信件保持不变。
- `remainingToday` 始终为有限 JSON 数字，不返回 `Infinity` 或负数，避免官方客户端禁用按钮或序列化异常。
- 不修改游戏安装目录中的 `feapp.dat`；当前 OliviaSoul 挂载方式保持不变。

### 错误处理

- 非整数、负数或大于 `10000` 的配置返回 HTTP 400。
- 数据库写入失败时沿用统一错误处理，不返回“保存成功”。
- 有限模式达到上限时，发送与重发使用相同的动态 429 提示。

## 测试设计

- 新安装/无设置时默认为不限量，连续发送至少 4 封均成功，列表和发送响应的 `remainingToday` 为 `9999`。
- 设置为 3 时保留现有行为：前三封成功，第四封返回 429，跨本地自然日恢复。
- 设置为 5 时前五封成功，第六封返回动态上限错误。
- 从有限模式切换为 0 后，当天已达到上限的账号可立即继续发送。
- 将 0 切回有限值后，现有当日计数按原统计口径生效。
- 失败重发在不限量和有限模式下分别覆盖。
- 今日重置在有限模式下恢复完整余量；不限量模式仍返回 `9999`。
- 管理 API 对边界值 `0`、`10000` 接受，对负数、小数、字符串和 `10001` 拒绝。
- 运行 `source/local-service` 全量测试，确认信件、记忆、远端导入和模型配置相关测试没有回归。
