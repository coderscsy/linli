# OliviaSoul 原生 MIDI 演奏与视频回信设计

日期：2026-08-31  
状态：待用户复核

## 背景与已确认事实

《BSide: Olivia Lin》离线客户端为 `ToyPianist-win-x64-rel-v0.0.9.627`，运行日志中的平台是 `pc_lite`。当前客户端通过 `WebPlayerManager` 播放已经渲染好的 MP4；本机 `cache/studio` 里只有 149 个 MP4（约 20.7 GB）及少量封面，没有 MIDI、动作谱、角色模型或 Unreal 工程资源。

客户端二进制仍保留 `LivePlayerManager`、`PerformanceManager`、`RenderPlaySource`、`startPlayingMusic` 和 IPC/Protobuf 消息相关代码，并期待原生渲染器位于 `wallpaper/TPRender/Binaries/Win64/Olivia.exe`。离线版本表还保留渲染包标识 `ovilia_Win64_Development_15918`，但游戏目录、本机缓存和停服备份中都没有 `TPRender` 本体。

原 MIDI 页面依赖官方对象存储和 `/midi/generate` 等服务，把 MIDI 转换为成品音频/视频；OliviaSoul 当前只接管登录、用户信息和信件接口，未实现 `/midi/*`。

## 视频回信能力边界

现有项目不是“没有视频回信”，而是已有能力和目标能力不同：

- 已有：导入官方已经生成的视频回信。
- 已有：通过 `POST /admin/api/letters/:id/video` 给一封已完成的文字回信挂载本地 MP4；游戏客户端可把它作为视频回信播放。
- 已有：校验 MP4、限制 512 MiB、支持 Range 播放，并随 `.soul` 记忆导出和恢复。
- 未有：Gemma 或 OliviaSoul 自动生成新的林离动画视频。当前回复 worker 只调用文字模型，并固定保存为 `reply_type = 1`。

本设计保留现有视频管理能力，并新增“渲染任务完成后可将结果自动挂到指定回信”的连接层。Gemma 仍负责文字内容；角色动作视频由独立 MIDI/角色渲染管线产生，不声称 Gemma 本身具备视频生成能力。

## 目标

- 接受标准 MIDI `.mid` 和 `.midi` 文件，不受官方每日生成次数限制。
- 在本机离线生成林离弹奏该 MIDI 的演奏，尽可能保证音符、琴键、手指、手臂、延音踏板和音频时间轴同步。
- 复用原生 `TPRender` 和林离资产作为首选，不替换为普通 MP4 套画面。
- 在原游戏 MIDI 页面显示本地任务的排队、分析、渲染、完成、失败、取消和重试状态。
- 生成的视频既可作为 MIDI 作品播放，也可由用户选择挂载为某封视频回信。
- 所有新增大文件、缓存、临时帧和输出均存放在 I 盘，不在 C 盘增加大型数据。
- 修改可回退；不得破坏现有 85 GB 停服备份、游戏离线曲库或信件记忆。

## 非目标与真实性边界

- 不破解 DRM，不绕过付费或账号权限，不下载来源不明的角色模型。
- 不重新分发米哈游的专有角色、模型、渲染器或游戏资源。
- MIDI 只包含音高、时间、力度、控制器等演奏数据，不包含人类指法。指法和手臂轨迹只能由规划器推导。
- 对超过十指、跨度不可能、双手交叉冲突或超出钢琴音域的编曲，系统必须给出“已自动简化”或“无法物理演奏”的提示，不能伪称完全真实。
- 第一阶段不能证明原生渲染器可用时，不承诺原版林离高保真输出，也不以套用旧视频冒充准确动作。

## 方案比较

### 方案 A：抢救原生 TPRender 并复原演奏协议（采用）

从用户本机旧安装、Steam 已拥有文件、官方公开下载元数据和现有日志中寻找匹配的 `TPRender` 包；使用客户端现存的 IPC/Protobuf 代码复原启动、就绪、模式切换、演奏计划、进度和结束消息。获得可执行渲染器后，再从最小音阶计划开始推导 performance 数据格式。

优点：角色、场景、钢琴和动画最接近官方。缺点：渲染包和官方 MIDI 到动作规划器均未保存在当前离线包，存在明确的不确定性。

### 方案 B：使用合法林离模型重建独立 3D 渲染器

如果用户以后能提供合法可用、允许本地修改的林离模型与骨骼资产，可在 Unreal、Unity 或 Blender 中重建钢琴、指法、IK 和摄像机管线。

优点：完全掌控离线渲染。缺点：现阶段缺少合法模型与原始动画资产，不能作为立即可落地方案。

### 方案 C：通用钢琴角色验证后再重定向

先用许可清楚的通用角色验证 MIDI 解析、指法规划、琴键同步、音频和视频录制，未来再替换角色。

优点：核心算法可独立推进。缺点：阶段结果不是林离，不满足本次最终目标，只作为方案 A 失败后的候选。

## 分阶段门槛

### 阶段 1：原生渲染器可行性验证

阶段 1 不修改游戏业务逻辑，所有探测工具放在 `<源码目录>`，资产、缓存和实验输出放在 `<用户指定的探测数据目录>`。

工作范围：

1. 建立渲染包清单和哈希，不移动或删除现有文件。
2. 从合法来源定位与 `ovilia_Win64_Development_15918` 匹配的 `TPRender`。
3. 分析 `NutLivePlayer.dll` 的 IPC/Protobuf 消息、进程参数和就绪握手。
4. 建立最小协议探针，只发送无害的启动、状态、停止和短音阶测试。
5. 记录进程退出码、日志、窗口状态和消息往返，所有失败均可重复诊断。

阶段 1 通过标准：

- TPRender 能在断网状态启动并进入 ready；
- 能加载林离、钢琴和原场景；
- 能让至少一个琴键及对应角色手部动作按本地事件发生；
- 能完成一段短音阶，并能观察到开始、进度和结束事件。

任一核心条件无法满足时，阶段 1 标记为阻塞，停止对游戏文件的修改，并向用户报告缺失资产或协议证据，再由用户决定是否转方案 B/C。

### 阶段 2：本地 MIDI 与动作规划器

阶段 1 通过后新增独立模块：

- `MidiParser`：支持 SMF 0/1、多轨、速度变化、拍号、力度、Note On/Off、延音踏板和常见控制器；拒绝损坏文件。
- `PerformanceNormalizer`：合并选定钢琴轨、处理重叠音符、静音轨、超音域和异常时长。
- `HandSplitter`：以音域、旋律连续性、跨度和时间窗口将音符分配给左右手。
- `FingeringSolver`：动态规划指法，惩罚不可达跨度、频繁跳跃、手指碰撞和不自然交叉。
- `MotionPlanner`：把手指、手腕、手臂、身体呼吸与踏板事件转换为原生 performance 计划，并做关键帧平滑。
- `RendererAdapter`：封装 TPRender 启动、ready、计划提交、进度、取消、退出和错误恢复。
- `CapturePipeline`：优先使用渲染器原生输出；没有原生导出时，以 FFmpeg 录制渲染窗口并与本地音频按统一时间戳合成 MP4。

“任何曲子”表示格式正确的 MIDI 都可以提交和分析，不表示每份超出人体能力的 MIDI 都能无损映射为十指演奏。系统在必须删减、移调或重新分配音符前默认暂停并要求用户确认；不静默丢音。

### 阶段 3：OliviaSoul 与原游戏接入

OliviaSoul 本地实现并接管：

- `POST /genObjectUploadUrl` 的本地替代流程；文件直接流入 I 盘任务目录，不使用官方对象存储。
- `POST /midi/generate`
- `GET /midi/getGenerateResult`
- `GET /midi/listJobs`
- `GET /midi/batchGetResult`
- `POST /midi/cancelGenerate`
- `POST /midi/deleteJob`
- `POST /midi/importShareCode` 返回明确的离线不支持状态，除非以后定义本地分享包格式。

客户端补丁：

- 接受 `.mid` 和 `.midi`；不通过改扩展名伪造格式。
- 文件上限变为可配置值，默认 50 MiB；服务端仍实施流式大小和 MIDI 头校验。
- 所有 MIDI 路由指向 OliviaSoul；任务列表、进度和结果继续使用原界面。
- `generatedToday` 和 `dailyLimit` 返回本地兼容值，不实施每日次数限制。
- 结果提供至少一个本地 MP4 URL和一个音频 URL，继续复用游戏现有播放器。

## 数据与存储

默认根目录：`<用户指定的探测数据目录>`。

- `inputs/`：用户原始 MIDI，文件名去路径化并使用任务 ID 隔离。
- `jobs/`：任务元数据、解析摘要、警告和状态日志。
- `plans/`：performance 计划和可复现实验数据。
- `cache/`：可安全重建的渲染缓存。
- `outputs/`：音频、视频、封面和校验摘要。
- `temp/`：渲染临时文件；成功或取消后按配置清理。
- `renderer/`：本地合法取得的 TPRender 包及其哈希清单。

OliviaSoul SQLite 增加 `midi_jobs` 表保存任务 ID、输入路径、原文件名、状态、进度、警告、错误、输出路径、创建/完成时间及可选的目标信件 ID。数据库只保存相对路径，服务端对所有文件请求做根目录约束，禁止 `..` 和任意绝对路径访问。

当前位于 `C:\Users\YOUR_NAME\AppData\Roaming\miHoYo\Olivia-steam\cache\studio` 的约 20.7 GB 官方缓存不在本设计中移动或删除。新增流程不得把视频帧、模型、渲染器或输出写到该目录。

## 视频回信接入

管理页的已完成文字回信增加“从 MIDI 生成视频回信”和“选择已完成 MIDI 作品”两个入口：

1. 用户选择目标回信和 MIDI。
2. Gemma 文字回信保持不变；MIDI 任务独立运行。
3. 渲染完成后，用户预览并确认。
4. 服务端复用现有 `saveReplyVideo`/`reply_video` 语义，把已校验的 MP4 复制或硬链接到视频回信目录；跨卷时使用流式复制和临时文件原子落盘。
5. 数据库事务把 `reply_type` 改为 2；失败时保留原文字回信，不出现半完成视频状态。
6. 原游戏继续通过 `replyVideoUrl` 播放；`.soul` 导出继续包含视频。

默认不自动把每个 MIDI 作品挂到回信，避免无意覆盖已有视频。若已有视频，必须明确确认替换；旧文件只在新文件落盘、校验和数据库提交都成功后才删除。

## 状态、错误与恢复

任务状态：`queued`、`analyzing`、`needs_confirmation`、`planning`、`rendering`、`muxing`、`completed`、`failed`、`cancelled`。

- 服务重启后，未开始任务恢复排队；渲染中的任务标记为可重试，不假设外部进程仍安全运行。
- TPRender 崩溃时保存退出码、最后 IPC 状态和渲染日志，不循环无限重启。
- 取消任务先发协议停止，再等待有限时间，最后只终止该任务启动并验证 PID/路径的渲染进程。
- 输出先写 `.partial`，通过 MP4/音频探测和时长校验后再原子改名。
- 删除任务默认只删除可重建的本地输入和输出，不影响已挂载的视频回信；删除已挂载资源必须二次确认。

## 测试与验收

阶段 1：

- 离线启动/停止渲染器至少三次，无残留进程。
- ready、按键、短音阶、进度、结束事件都有可复现日志。
- 原游戏安装文件在探测阶段哈希不变。

MIDI 管线：

- SMF 0、SMF 1、多速度段、延音、重叠音、左右手和多轨选择。
- 音阶、和弦、琶音、快速重复音、跨手、超十指、超音域、损坏文件和超大文件。
- 简单曲目的 Note On 与琴键事件误差目标不超过一帧；音频与视频起止误差目标不超过 50 ms。
- 不可物理演奏的 MIDI 必须进入确认状态或失败，不能静默丢音。

API/界面：

- 上传、列表、轮询、取消、重试、删除、服务重启恢复和不限次数。
- 路径穿越、伪造扩展名、错误 MIDI 头、超限文件及并发重复请求。
- 原信件、记忆、手动视频挂载、远端视频导入和 `.soul` 导入导出测试全部回归通过。

视频回信：

- 新视频成功挂载、替换确认、Range 播放、删除、导出和恢复。
- 渲染或复制失败时原文字/原视频保持不变。

## 部署与回退

- 运行版同步前备份 OliviaSoul 数据库、服务文件和客户端资源；所有备份存放 I 盘。
- 提供一键卸载挂载和恢复原 `feapp.dat` 的路径。
- 不改动 `<用户备份目录>`；该目录继续作为停服时点的只读基线。
